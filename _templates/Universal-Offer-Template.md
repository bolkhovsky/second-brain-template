# Универсальный шаблон коммерческого предложения v2

## Ключевое изменение: Design Sprint

**Почему Design Sprint обязателен:**

- Снимает техническую неопределённость ДО крупных инвестиций
- Клиент видит результат через 7 дней и принимает решение
- Минимизирует риски обеих сторон
- Даёт точную оценку MVP вместо "примерной"

---

## Структура документа (обновлённая)

```
1. Титульная часть
2. Краткое описание проблемы
3. Подход: Design Sprint → MVP → Масштабирование
4. Design Sprint: детальное описание (ОБЯЗАТЕЛЬНО)
5. Архитектура решения
6. Следующие этапы (после Design Sprint)
7. Инфраструктурные расходы
8. Обо мне
9. Следующие шаги
10. Контакты
```

## 3. ПОДХОД: Design Sprint → MVP → Масштабирование

```markdown
## 2. Подход: Design Sprint → MVP → Итерации

В настоящий момент есть техническая неопределённость: 
[описание неопределённости — например, эффективность разных подходов, 
особенности интеграции, качество данных]. 
Поэтому требуется выполнить изыскания для выработки оптимального подхода.

Вместо длительной разработки «под ключ» с неопределённым результатом 
я предлагаю поэтапное внедрение с валидацией на каждом шаге:

| Этап | Что вы получаете | Решение о продолжении |
|------|------------------|----------------------|
| **Design Sprint** (7 дней) | Работающий прототип на реальных данных | Видите результат → принимаете решение |
| **MVP** (4–6 недель) | Рабочая система для ежедневного использования | Оцениваете экономию времени |
| **Масштабирование** | Пакетная обработка, автоматизация рутины | Выходите на полную мощность |

### Почему так:
- **Минимальные риски:** после Design Sprint понятно, работает ли подход
- **Гибкость:** можете остановиться или скорректировать на любом этапе
- **Прозрачность:** оплата по факту выполнения, без скрытых расходов
```

## 4. DESIGN SPRINT: ДЕТАЛЬНОЕ ОПИСАНИЕ (ОБЯЗАТЕЛЬНЫЙ БЛОК)

```markdown

✅ **Анализ реальных данных**
Изучим [X–Y] примеров [документов/процессов/обращений], 
выявим паттерны и граничные случаи.

✅ **Прототип системы**
Создадим [консольный инструмент / бота / скрипт], который:
- Принимает на вход: [входные данные]
- Выполняет: [ключевые операции]
- Выдаёт: [результат в структурированном виде]

✅ **Тестирование на реальных данных**
Прогоним прототип на ваших реальных [документах/данных], 
оценим точность и качество.

✅ **Детальный план дальнейшей разработки**
На основе результатов подготовим точную оценку MVP 
с учётом выявленных особенностей.

### Что вы получите через 7 дней

📄 **[X–Y] обработанных [единиц]**

ваши [сотрудники/эксперты]. Оценить качество, скорость, точность.

📊 **Технический отчёт**
- Какие типы [операций] система обрабатывает отлично
- Какие требуют доработки
- Рекомендации по архитектуре для MVP

💰 **Точная оценка следующих этапов**
Детальный план и бюджет MVP с учётом реальной сложности ваших [данных].
```

# СКРИПТЫ ДЛЯ АДАПТАЦИИ

## Описание неопределённости:

```
В настоящий момент есть техническая неопределённость: 
[выбрать нужное]
- эффективность разных подходов (алгоритмический, на основе ИИ, гибридный)
- качество и полнота исходных данных
- особенности интеграции с [система клиента]
- точность распознавания [тип контента]
- производительность при обработке [объём]

Поэтому требуется выполнить изыскания для выработки оптимального подхода.
```

## Обоснование Design Sprint:

```
Почему Design Sprint, а не сразу разработка:

1. **Вы видите результат через 7 дней** — не через месяцы
2. **Минимальные инвестиции** — [XXX 000] ₽ вместо [X млн] ₽
3. **Точная оценка** — после спринта я знаю реальную сложность
4. **Ваше решение** — продолжать, скорректировать или остановиться
5. **Оплата за результат** — 100% после сдачи, не авансом
```

## Переход от Design Sprint к MVP:

```
После успешного Design Sprint:

✅ Вы видели систему в работе
✅ У вас есть [X] обработанных [единиц] для сравнения
✅ Вы знаете точную стоимость и сроки MVP
✅ Вы принимаете решение на основе фактов, а не обещаний

→ Если результат устраивает — переходим к MVP
→ Если нужны корректировки — обсуждаем
→ Если не подходит — вы потеряли только [XXX 000] ₽, а не [X млн] ₽
```

# КОГДА Design Sprint НЕ НУЖЕН

В редких случаях можно пропустить Design Sprint:

1. **Типовой проект** — уже делали аналогичное 3+ раз
2. **Простая интеграция** — известные API, стандартные форматы
3. **Клиент настаивает** — понимает риски и готов к ним
4. **Очень маленький бюджет** — Design Sprint = 30%+ от всего проекта

В этих случаях заменяем на:

- Расширенный этап анализа (3-5 дней в рамках MVP)
- Поэтапную оплату с валидацией после первого этапа
